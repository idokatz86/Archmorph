# Phase 2: Product and technology landscape

**Checked:** 2026-11-23

**Scope:** Current public documentation and vendor primary sources for build-time agents, runtime models, orchestration, protocols, Azure grounding/governance, adjacent migration products, and software-factory practices. Status and pricing can change; verify region, plan, and quota again before implementation.

## Executive assessment

The landscape supports a deliberately small, evidence-first Archmorph: deterministic workflow and typed architecture state, with models used for bounded tasks; official Azure catalogs and prices as ground truth; compiler/policy/preview checks before any deployment suggestion; and user approval for side effects. An autonomous multi-agent system, a managed gateway, or a full software factory is not a prerequisite for the product's core job.

The remote coding capability that could continue while the laptop is closed is GitHub Copilot's cloud experience / cloud agent. Its new cloud experience requires a paid Copilot plan and may be restricted by organization policy. The signed-in account's plan and additional-usage budget are unknown, and **no cloud task is running now**. The project prompt's Gate A and later implementation gates still apply: do not start cloud development until the user has approved the required gates.

## Build-time coding and model economics

- **Copilot cloud agent:** GitHub documents the new “Copilot in the cloud” experience as available on paid Copilot plans from 2026-10-28, subject to organization/enterprise policy. Sessions can run in a cloud sandbox, GitHub Actions environment, or remote environment and can continue across supported clients. The official docs list Copilot cloud agent as available for paid plans; Free retains the older Chat experience. See [Copilot on GitHub.com and Mobile](https://docs.github.com/copilot/concepts/copilot-surfaces/copilot-on-github).
- **Plan/budget unknown:** current published individual plans include base AI-credit allowances (Pro 1,000, Pro+ 3,900, Max 10,000), with optional flex amounts that vary by plan. The user's plan, remaining credits, and stop-at-budget setting were not verified in Phase 0. Cloud work consumes usage; no plan or budget setting was changed. See [GitHub Copilot plans](https://docs.github.com/copilot/get-started/plans-for-github-copilot).
- **Copilot Fusion:** generally available on VS Code, Copilot CLI, the Copilot app, JetBrains, and Copilot in the cloud. It routes/orchestrates model calls by effort and task; usage is charged per model at its standard rate. GitHub's 30% paid-plan discount is temporary through 2026-11-30, not a durable cost assumption. Fusion can improve model selection but makes exact per-task model choice less predictable. See [Copilot Fusion](https://docs.github.com/copilot/concepts/models/copilot-fusion) and the [GA announcement](https://github.blog/changelog/2026-10-28-route-and-orchestrate-models-with-github-copilot-fusion/).
- **Runtime models:** the repository defaults to Azure OpenAI `gpt-4.1` with `gpt-4o` fallback; these differ from Copilot build-time billing. The current Foundry catalog lists GPT-5.4, GPT-5.5, GPT-5.3-Codex and other model families, but model availability, deployment type, price, and quota vary by region and cloud. Do not select from a global model list alone. See [Foundry Models sold by Azure](https://learn.microsoft.com/azure/foundry/foundry-models/concepts/models-sold-directly-by-azure) and [Azure OpenAI pricing](https://azure.microsoft.com/pricing/details/azure-openai/).
- **Evaluation quality:** the May 2026 benchmark report is synthetic and tiny; the later plan says production routing stays unchanged until live quality, cost, latency, safety, quota, and rollback gates pass. Treat its model rankings as hypotheses, not current product evidence.

## Orchestration and interoperability

- **Microsoft Agent Framework:** offers agents, a harness, workflows, and model/MCP integrations across .NET, Python, and Go. Its own guidance says to use a function instead of an agent when a function suffices. The Go framework is public preview; C# Foundry package examples use `--prerelease`; the Durable Extension's setup also uses prerelease packages. It is a candidate for a future durable workflow, not an automatic replacement for Archmorph's current application pipeline. [Overview](https://learn.microsoft.com/agent-framework/overview/) · [Durable Extension](https://learn.microsoft.com/agent-framework/hosting/durable-extension).
- **Alternatives:** [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) is a low-level graph/runtime with persistence and human-in-the-loop control; [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) provides a smaller agent/tool/guardrail/tracing abstraction. Neither creates a need to adopt agent orchestration for deterministic catalog lookup, transformation, export, or validation.
- **MCP:** latest specification linked from `latest` is 2026-07-28. MCP standardizes tools/resources/prompts over JSON-RPC; it does not enforce consent or safe tool behavior. The spec says tool descriptions/annotations must be treated as untrusted unless the server is trusted. [Specification](https://modelcontextprotocol.io/specification/latest).
- **A2A and AG-UI:** A2A's latest released protocol is 1.0.0 and is for communication/delegation between independent agents; AG-UI 1.0 standardizes agent-to-application event streams. Both are optional integration protocols, not core requirements for a single-user migration workbench. AG-UI explicitly treats model output as untrusted and calls for consent around side-effectful tools. [A2A 1.0 specification](https://a2a-protocol.org/latest/specification/) · [AG-UI 1.0 specification](https://docs.ag-ui.com/spec/1.0).
- **Entra Agent ID:** generally available for agent identity and access management; local-agent authentication and some blueprint flows are preview. This is relevant only if an Archmorph agent needs its own governed identity to call resources; it does not replace least-privilege app identity or user approval. [What's new](https://learn.microsoft.com/entra/agent-id/whats-new-agent-id).

## Azure grounding, validation, and governance

- **Prices:** Azure Retail Prices API is unauthenticated and exposes retail rates, not negotiated prices or actual bills. It is useful for grounding estimates when paired with SKU, usage, region, timestamp, and assumptions. [API overview](https://learn.microsoft.com/rest/api/cost-management/retail-prices/azure-retail-prices).
- **Reusable infrastructure:** Azure Verified Modules (AVM) provide Bicep and Terraform resource/pattern modules. AVM has explicit module lifecycle states (including proposed, available, orphaned, and deprecated); verify and pin the specific module and version rather than treating “AVM” as a blanket certification. [AVM home](https://azure.github.io/Azure-Verified-Modules/) · [module lifecycle](https://azure.github.io/Azure-Verified-Modules/specs/shared/module-lifecycle/).
- **Validation:** Bicep build/lint and Terraform fmt/validate should run locally or in CI against generated artifacts; policy-as-code (for example AVM policy-library checks) should reject unsafe results. Bicep what-if does not change resources, but it requires the same permissions as deployment and cannot guarantee that the later deployment succeeds. It is a preview, not authorization or a safety proof. [Bicep what-if](https://learn.microsoft.com/azure/azure-resource-manager/bicep/deploy-what-if).
- **MCP tools:** Azure MCP supports read-only mode, but its documented default is `false`; high-risk command confirmation should remain enabled. ARM MCP exposes both read tools and write-capable deployment/resource tools, including `create_deployment`. Any future agent integration must explicitly restrict namespaces/tools, use read-only mode by default, and gate writes behind user approval. [Azure MCP tool configuration](https://learn.microsoft.com/azure/developer/azure-mcp-server/tools/) · [ARM MCP tool reference](https://learn.microsoft.com/azure/azure-resource-manager/management/azure-resource-manager-mcp-tools).
- **Gateway:** Azure AI Gateway is GA and offers centralized model/tool access, quotas, budgets, policies, and telemetry. Its free request tier is attractive for a prototype, but the published paid base tier is above the stated budget; compare current regional pricing before adoption. [GA and pricing announcement](https://techcommunity.microsoft.com/blog/IntegrationsonAzureBlog/azure-ai-gateway-is-now-generally-available-ship-faster-stay-in-control/4572644).

## Software-factory practices

- [GitHub Spec Kit](https://github.com/github/spec-kit) provides a spec-driven workflow (specification, plan, tasks, implementation) and supports multiple coding agents. It can supply process ideas without adopting every extension or automating approvals.
- GitHub Copilot cloud agent and VS Code support repository/path instructions and `AGENTS.md`; use concise repository-level instructions, explicit validation commands, scoped tool access, and human-reviewed pull requests. [Custom-instruction support matrix](https://docs.github.com/copilot/reference/custom-instructions-support).
- StrongDM's [Software Factory essay](https://factory.strongdm.ai/) describes non-interactive code generation, scenarios/holdouts, and behavioral service twins, and advocates no human-written or human-reviewed code plus at least $1,000/day per engineer in tokens. Those are the author's claims, not independently validated economics or a safe default for Archmorph. Borrow the idea of held-out user scenarios and adversarial integration tests; reject removal of human review, budget discipline, or release gates.

## Landscape conclusion and Gate A boundary

The evidence favors retaining a deterministic workflow with narrow model calls and strong provenance, not rebuilding around a generic autonomous agent. Use cloud coding only when explicitly approved, budgeted, and started as a GitHub cloud task; the laptop can be closed only after the remote task is confirmed running and its repository/branch, tests, and persistence are verified. That condition is **not met now**. This report does not authorize implementation, production access, deployment, or decommissioning.
